# 如何从“只能 Mimo 用”查到原生控制

## 第一阶段：区分手机按键和云台事件

ADB 普通 shell 可以执行 getevent 和 dumpsys input，SELinux 保持 Enforcing。开始时枚举 13 个输入节点。

手机音量＋可以在 Mimo 中触发录像；手机独立抓拍键也能操作原生录像。这只证明相机能接受某些输入，不代表 OM8 使用同一路径。手机抓拍键观察到 BTN_TRIGGER_HAPPY24/18，与 OM8 后续的 KEY_VOLUMEUP 不同。

在 Mimo 录像、停止、变焦成功的受控样本中，OM8 未产生可见 evdev 事件；原生相机中也无响应。曾误点屏幕的样本已排除。已有 uinput 设备声明支持 KEY_CAMERA 等按键，不能单凭能力表就认定它属于 OM8。

## 第二阶段：BLE 线索不足以认定拍摄命令

Mimo 重连时，选定的 Bluetooth/GATT 框架日志显示 LE 连接、服务发现、通知订阅及持续通知回调。但没有可解释的通知载荷。

手机生成的 bugreport 中实际找到的 42 个 BTSnoop 文件均只有 16 字节头。已有 localhost HCI 调试流通过普通 ADB forward 能读到命令/事件，但持续没有 ACL 数据。这个入口不能当作完整 ATT/GATT 抓包。

因此没有把某个 UUID、通知频率或厂商事件猜成录像指令，也没有向设备发送猜测的握手数据。原始蓝牙日志、完整报告、扫描列表和截图都不在本仓库。

## 第三阶段：配对后出现标准输入设备

用官方 nRF Connect 4.29.1 排查普通第三方连接，用户执行 Bond 后，画面确认 OM8 候选显示 BONDED。输入节点由 13 个变为 15 个，新设备名称与 OM8 匹配，总线标识 0x0005，使用 Generic.kl。

节点编号 event13/event14 是当时分配结果，不能硬编码到其他手机或重连后的程序。输入设备名也不是不可伪造的身份认证；本次结合用户持有的 OM8 与受控实体按键操作确认归属。

单次实体录像键测试得到 KEY_VOLUMEUP DOWN/UP。后续原生相机用户确认录像成功，拨轮平滑变焦至 8×，专用切换键能够切前后镜头。对应事件为 KEY_ZOOMIN/KEY_ZOOMOUT、KEY_VIDEO_NEXT。

这些名称是 **Linux evdev key labels**，不要把对应 Linux 数字直接传给 Android `input keyevent`，也不要由 ADB shell 的权限推断普通 Android 应用可以随意注入事件。

## 样本质量与限制

| 本地测试编号 | 可公开结论 | 限制 |
| --- | --- | --- |
| 32 | 单次 OM8 录像键产生一组 VOLUMEUP | 这一轮前台是诊断工具，不是原生相机 |
| 33 | 用户确认原生录像控制成功 | 窗口中有多次拨轮和两组录像键，不能当作严格单次开始/停止对照 |
| 36 | 原生变焦由 1× 到 8×，用户报告平滑 | 7 组 ZOOMIN、5 组 ZOOMOUT；不能据此标定一秒或每格倍率 |
| 37 | 未识别侧轮按压独立键 | 两次按压的反馈伴有缩放和触屏事件，不能证明永远没有独立事件 |
| 38 | 专用切换键成功切前后镜头 | 有 3 组 VIDEO_NEXT 和其他混合动作；未验证所有模式或录像途中切换 |

还发现 nRF 的 UI 自动化树未暴露实际扫描条目。最初由“树中无条目”推断“画面为空”不可靠；用本地截图与本地 OCR 交叉检查后更正。这是本次观测方法的限制，不能当成用户没操作或系统权限失败。

## 最终实现评估

当前设备与设置下，原生相机直接消费标准输入事件，已经满足录像、变焦、镜头翻转目标，故不需要桥接应用。没有 Root、修改固件、绕过系统权限或重映射现有缩放键。

如果其他设备能收到标准键但相机不响应，可以另行评估用户授权的无障碍服务；本项目没有实现或验证该路线。若连标准键都收不到，也不能假定某个固定 BLE UUID 就能解决。

## 数据发布方式

`evidence/find-x9-ultra.json` 是由本地样本整理的白名单摘要，不是原始日志。移除了序列号、MAC、具体设备广播名、主机路径、精确时间、进程信息和其他应用信息。原始资料未发布，因此公众可以检查结论与摘要的一致性，但无法从这个仓库独立重放全部蓝牙流量。
